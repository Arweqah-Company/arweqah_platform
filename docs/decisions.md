# Decisions

Short records of choices that are not obvious from the code. Newest first.

## 2026-10-21 — Phase 1: sign-in, organization, employees, interface

| # | Decision | Why | Revisit when |
|---|---|---|---|
| 19 | No passwords: sign in with Microsoft or the work e-mail, always with a 6-digit code from an authenticator app; the app is mandatory for everyone and the code is required in every session, also after Microsoft | Owner's rule; removes password storage, resets and phishing of passwords | Passkeys are wanted |
| 20 | Custom TOTP sign-in plugin (RFC 6238) on Better Auth; secrets encrypted with `FieldCipher`, backup codes and invite tokens stored hashed, 5 failures lock 15 min, replay blocked by `last_used_step`, identical errors | Better Auth has no e-mail + TOTP-only sign-in | Better Auth ships it |
| 21 | The e-mail step answers whether it is a first sign-in and e-mails the QR link (one per minute per address) | Owner wants the system to recognize a first time; reveals only "active account without an app", and only the mailbox owner receives anything | Enumeration becomes a concern |
| 22 | Organization is dynamic per company: levels, units (closure table), job titles; changing levels that hold data needs an impact preview + token + confirmation; soft deletes | Owner's rule: never delete employees silently | — |
| 23 | Employee ID number, IBAN and salary are encrypted; ID is searchable and unique through an HMAC blind index (`BLIND_INDEX_KEY`); masked without `employees.view_sensitive` | Sensitive data, PDPL | Key rotation procedure is needed |
| 24 | `EmployeePlacementPort` (org contract) implemented by employees | Avoids a circular module dependency | — |
| 25 | Every e-mail is logged in `email_logs` (status, error, server reply), never the body; `LoggedMailSender` wraps SMTP | Delivery must be traceable; bodies hold one-time links | — |
| 26 | E-mail through Office 365 SMTP (`smtp.office365.com:587`, STARTTLS) with the shared mailbox | Owner's mailbox; SMTP AUTH must be enabled on it | Moving to SES in production |
| 27 | API modules are split by kind of file (entities, types, errors, contracts, rules, permissions; services, policies, transformers, messages; repositories, adapters, jobs; controllers, dtos); audit action names are constants in `application/messages` | Owner's code-architecture rule, enforced through the `module-architecture` skill | — |
| 28 | Dashboard surfaces use derived cool neutrals and white (page `neutral-50`, panels white, borders `neutral-200`); brand cream and beige stay for sign-in, e-mails and print; primary buttons are `ink` | Owner supplied reference screens | Brand owner objects |
| 29 | Input borders follow the reference (light `neutral-200`, 1.3:1), below the 3:1 of WCAG 1.4.11; labels, placeholders and the focus border carry the affordance | Owner's decision; documented trade-off | An accessibility audit asks for 3:1 (`neutral-500` is ready) |
| 30 | Sidebar: menus with sub-menus (People, System administration, My account), flush to the end edge and sticky; icons only when collapsed; lists become cards under 640 px | Owner's navigation and mobile rules | — |
| 32 | Every list page uses one toolbar (`ListToolbar`): search, a filter panel with removable chips, and a table / cards switch remembered per list in `localStorage`; large lists filter on the server (employees, audit log, e-mail log, notifications), small ones in the browser (companies, roles) | Owner's rule for all tables; one pattern to reuse for every future module | A list needs saved filters or export |
| 41 | Light and dark theme through CSS variables: components use semantic colors (`fg`, `link`, `primary`, `success`, `warning`, `danger-text`) and the existing surface tokens, which `theme.css` re-points under `html[data-theme=dark]`; `public/theme-init.js` sets the theme before first paint (a file, not inline, for the strict CSP); the choice lives in `localStorage.theme` and on the account (`users.theme`), a saved light or dark applies on a new device, "system" (the default) keeps the browser's own choice | One component set for both themes; contrast measured for the dark pairs (text 14.9:1, links 8.9:1, control borders 4.0:1) | The brand owner supplies a dark palette |
| 42 | Own profile (`GET/PUT /me/profile`, self-scoped, no permission key like notifications): a person changes the language, the theme, and **three** contact details (personal phone, personal e-mail, English name); name, number, placement, contract, ID, IBAN and salary stay HR's; sensitive fields are never returned; the audit log records field names only | The owner asked that users edit their own profile without saying which fields: the smallest safe set was chosen (low risk, no business rule) | The owner lists more self-service fields (e.g. work phone, photo) |
| 43 | Microsoft sign-in is closed by a step-by-step guide (`docs/microsoft-sign-in.md`) and `npm run microsoft:check`, which verifies the values and asks Microsoft whether the client id, secret and tenant are accepted | The only blocker left is the app registration in the company tenant; the check turns "try and guess" into a precise message | — |
| 44 | Microsoft sign-in can authenticate with a certificate (private_key_jwt via Better Auth `clientAssertion`) instead of a client secret; exactly one of the two is allowed | The owner's tenant blocks client secrets by policy; the private key stays outside the repo | Tenant allows secrets and prefers them |
| 45 | Production runs on one EC2 host with PostgreSQL, RabbitMQ and uploaded files in Docker volumes (daily backup script) and Let's Encrypt HTTPS; deploys log in to GHCR with the workflow's own token and ship the compose file with the code | Owner has a single server and a domain; fewest moving parts, no stored registry password; RDS / S3 stay a `.env` switch | Data volume or availability needs grow (move to RDS / S3) |
| 46 | Staging uses two domains (`stg-portal.arweqah.sa` web, `stg-api-portal.arweqah.sa` API) on one server and one certificate; the browser app still calls `/api` on its own domain, so `APP_URL`/`API_URL` are the web domain | A separate API origin for the browser would need CORS with credentials, a cookie domain and a CSP change and would weaken first-party cookies; the API domain stays for integrations | An external client needs the API origin as its only entry |
| 39 | The organization page offers a chart (HTML and CSS, no canvas: cards joined by border lines, zoom steps as classes, fit measures the content and scrolls to the middle) and a table of the same units; levels get brand colors in order petrol, green, orange, ink-outline with a text badge and a legend so color never carries the meaning alone; the root company card is `ink` | Owner's reference chart; readable, printable, no extra library | A tree beyond a few hundred units needs virtualization |
| 40 | Alerts are colored by meaning (success green, information yellow, warning orange, error red) with an icon and a 4 px start rule; text stays `ink` or the dark shade of its hue | Owner's rule; yellow only as a fill and rule, never as text | — |
| 37 | Error pages: one `ErrorPage` for 401, 403 and 404, with a brand-colored SVG picture (three digits, the middle one an icon badge); 403 comes from a route guard fed by each navigation item's permission, 401 only when a signed-in person's session ends (`/401`), a visitor goes to sign-in | Owner's reference design for all three pages | A module needs a different guard than its navigation item |
| 38 | Browser e2e uses its own API on port 3100 against the test database, with the sign-in limit raised (`SIGN_IN_RATE_LIMIT`, refused above 10 in production), e-mail pointed at a closed port, and a signed-in browser state saved once by global setup | The old setup reused whatever listened on port 3000 (a development server on the development database) and hit the 5/min sign-in limit | — |
| 33 | Export and import run in the browser: export builds the file from what the list API returns (page or all results, up to 10,000 rows), import reads the file, checks each row with the shared zod schema and saves valid rows through the normal create endpoints (3 at a time), so permissions, scopes, uniqueness and audit stay in the API | One implementation for every list; no second write path to secure | Imports above 1,000 rows or background processing are needed |
| 34 | Excel with `write-excel-file` + data-validation plugin and `read-excel-file`; CSV by our own parser | `exceljs` carries a moderate `uuid` advisory; the plugin is pinned to 1.0.0 because 1.0.2 is younger than 14 days | The plugin ages past 14 days (1.0.2) |
| 35 | Import is offered for employees and companies only; audit log, e-mail log and notifications are system records (export only); roles are permission-sensitive (export only) | Importing records the system writes itself, or permissions, would bypass its rules | A module asks for it |
| 36 | `npm run verify` is the end-of-task gate (architecture, design, testing, security) and a `UserPromptSubmit` hook reminds Claude on every prompt; shared code lives in `common/`, `core/`, `shared/` and is never copied (jscpd < 3 %) | Owner asked for these checks after every task and for no duplicated code | — |
| 30b | The sidebar is a floating panel rounded on all corners again (24 px), sticky; all panels, tables, dialogs and inputs keep rounded edges | Owner's visual rule | — |
| 31 | `SEED_DEMO_ORG` (development only, refused in production) fills each company with a sample structure | Empty structure made the screens look broken during development | — |

## 2026-10-19 — Foundation

| # | Decision | Why | Revisit when |
|---|---|---|---|
| 1 | Build fully custom on NestJS + React; no Frappe/ERPNext | Product owner's choice after comparing; full control of UX and data model | — |
| 2 | Monorepo with `apps/api` and `apps/web`, each organized by modules; a small `packages/shared` for zod schemas and DTO types only | Owner wanted backend and frontend separated; the contracts package avoids defining every shape twice. Removing it later means generating types from OpenAPI instead | If the apps move to separate repositories |
| 3 | NestJS 11.2 instead of 12 | `nestjs-zod` 5.5 supports NestJS ≤ 11 | `nestjs-zod` supports 12 (also fixes the moderate js-yaml advisory via swagger 12) |
| 4 | TypeScript 5.9 | `ts-jest`, `typescript-eslint` and `@nestjs/cli` do not support 6/7 yet | Tooling supports TS 7 |
| 5 | Vitest (with SWC for decorator metadata) for API tests instead of Jest | Better Auth and its Nest integration are ESM-only; Jest cannot `require` them | — |
| 6 | `.npmrc` `legacy-peer-deps=true` | npm 10 arborist crashes (`edgesOut` of null) on Better Auth's many optional peer dependencies; peers we need are listed explicitly | npm fixes the bug |
| 7 | Better Auth with session cookies instead of the team's JWT access/refresh pattern | Owner chose Better Auth for Microsoft sign-in and 2FA; HttpOnly session cookies keep tokens out of JavaScript | — |
| 8 | Microsoft accounts link to employees by email, only inside the company tenant | Entra emails are not verified across tenants; with a single-tenant app the company controls the addresses. Boot fails if the tenant is `common`/`organizations` | Microsoft identifiers (oid) are stored on employee records |
| 9 | Dynamic roles + scoped permissions (own/team/department/branch/company) owned by `core/access`; user placement also lives there | Scopes are computed from placement; keeps the org module free of authorization logic | — |
| 10 | Out-of-scope records return 404, not 403 | Do not reveal that a record exists | — |
| 11 | RabbitMQ instead of BullMQ; delayed work in a `scheduled_jobs` table moved to the outbox when due; Redis dropped | Owner chose RabbitMQ; it has no durable delayed delivery without a plugin, and the outbox keeps events consistent with the database | Several API instances need shared rate limits → add Redis as Better Auth secondary storage |
| 12 | XState machines run in-process; state persisted as XState snapshots with an optimistic `revision` | Approvals last days; persistence and locking matter more than in-memory actors | — |
| 13 | Entities listed explicitly in `database/entities.ts`; migrations loaded only by the CLI data source | Globs loaded through `require` broke under Vitest and hid entities from type checking | — |
| 14 | Foreign keys declared on entities as constraint-only relations by entity name | `migration:generate` stays clean (no drift) without importing other modules' classes | — |
| 15 | Rate-limit and audit IP from `X-Forwarded-For`, which the edge nginx overwrites with `$remote_addr`; Express trusts only private-network proxies | Clients cannot spoof their address | — |
| 16 | `max-params` replaced by a lint rule that exempts constructors; component length limit 80 lines in `.tsx` | DI constructors legitimately take many dependencies; JSX is mostly markup | — |
| 17 | React Router 8, Vite 8, TanStack Query 5, MSW 3: latest stable releases at least two weeks old | Team rule for new projects | — |
| 18 | Hosting: AWS `me-south-1` until the Saudi region opens (expected December 2026) | Owner's choice; needs documented legal basis for personal data meanwhile | Region opens |
